AI-Powered Refund Automation: Building a Reliable LLM-Based Dispute Resolution Architecture

September 2026 · Rajender Karra

A customer submits one angry paragraph. Inside it are several different accusations: some are supported by evidence, some are contradicted, and one may be impossible to verify. How should an AI system decide what to refund without paying twice or quietly rejecting a legitimate complaint?

The Refund Bench treats the complaint as a set of separate claims. It extracts each grievance, evaluates it against a frozen evidence snapshot, asks several independent LLM judges for a ruling, counts their votes in code, and lets deterministic business rules decide how much money can move.

The customer complaint

Consider this complaint from a food delivery app:

“Ordered at 8:15pm and the food showed up at 9:40pm. We had guests over, it was embarrassing. Two of the four were missing completely. The raita had leaked all over the inside of the bag. And the delivery guy was rude when I asked him about it. Honestly the worst experience I've had on this app - refund everything.”

A human may see this as one emotional complaint. The system should see four checkable grievances:

  1. Late delivery: the order arrived 85 minutes after it was placed.
  2. Missing items: two of the four Hyderabadi Biryani units were not delivered.
  3. Packaging problem: the raita container leaked inside the delivery bag.
  4. Partner conduct: the delivery partner behaved rudely when asked about the missing items.

The extractor should ignore “we had guests over, it was embarrassing” because it is context and emotion. It should ignore “the worst experience I've had” because it is an opinion. It should ignore “refund everything” because it is a demand, not a claim that evidence can verify.

Therefore, this complaint produces four grievances. That number is not just useful for reporting. It determines the judging workload: four grievances multiplied by three independent judges creates twelve judgement calls.

What the system needs

A production implementation needs an API service, an LLM provider with structured output, a database, a durable queue, background workers, and a payment integration. The system should also provide logs, metrics, tracing, retries, dead-letter handling, and a human-review interface.

The most important boundary is that the LLM does not directly control the payment amount. The model can interpret evidence and write an explanation. Application code counts votes, applies pricing rules, enforces the approval cap, and authorizes money movement.

Decision workflow The six stages below describe the business decision workflow performed inside that system.

The first model call receives the complaint and the order's line items. It identifies statements about events or conditions that evidence could confirm or contradict.

Notice that “two of the four” has been made self-contained by resolving it against the order. The same process resolves vague references such as “him” and “it”. The extractor must not decide whether the claims are true. Extraction and judgement are separate stages.

Stage 2: Freeze the evidence

Before any judgement begins, the system creates an immutable evidence snapshot. A typical snapshot might contain the order timestamps, delivery SLA, line items, pickup weight, partner rating, and any recorded packaging information. 

{
  "order_id": "order-1840",
  "placed_at": "20:15",
  "delivered_at": "21:40",
  "delivery_sla_minutes": 45,
  "line_items": [
    { "name": "Hyderabadi Biryani", "quantity": 4, "unit_price": 320 },
    { "name": "Raita", "quantity": 1, "unit_price": 60 }
  ],
  "pickup_weight_expected_kg": 2.4,
  "pickup_weight_actual_kg": 1.2,
  "partner_rating_at_handover": 5,
  "packaging_condition_recorded": false
}

The snapshot matters because operational data changes. A partner rating may be updated, a bill may be edited, or a reconciliation job may run later. If a retry observes different evidence, the same dispute could receive a different result. Every judge must see the same snapshot, identified by a version or content hash.

Stage 3: Ask independent judges

Each grievance is sent to three independent judges. With four extracted grievances: 

4 grievances x 3 judges = 12 judge calls

Each judge receives one grievance and the same evidence snapshot. Judges do not see one another's responses. Otherwise, later judges may anchor on earlier answers and the system will count one opinion three times instead of counting three independent opinions.

Judging prompt

You are an impartial claims adjudicator.

Rule on the following grievance using ONLY the evidence given.

Grievance: {{grievance_text}}
Evidence:  {{evidence_snapshot_json}}

Rulings:
- UPHELD: the evidence supports the grievance.
- REJECTED: the evidence contradicts the grievance.
- ESCALATE: the evidence is silent or ambiguous.

Rules:
- Pick exactly one ruling.
- Do not reason about what is typical, likely, or fair.
- Rule only on the evidence provided.
- If the evidence does not address the grievance,
  return ESCALATE, never REJECTED.

Schema:
{
  "ruling": "UPHELD" | "REJECTED" | "ESCALATE",
  "confidence": 0.0,
  "evidence_cited": "<fields used>",

Stage 4: Count votes in code

The application counts the rulings. It does not ask another model to determine the majority.

How the bench turns judge votes into an outcome
GrievanceEvidenceVotesOutcome
g1: Late delivery85 minutes versus a 45-minute SLAU, U, UUpheld
g2: Missing itemsPickup weight was half the expected weightU, U, UUpheld
g3: Leaked raitaNo packaging evidence existsU, E, EEscalate
g4: Rude partnerFive-star rating at handoverR, R, RRejected

The split for g3 is valuable. One judge believed the complaint, but two recognized that the evidence was silent. The result is escalation rather than an automatic refund. A 3-0 verdict is stronger than a 2-1 verdict, even when the majority outcome is the same.

Stage 5: Calculate the refund in code

Deterministic business rules calculate the amount. For this example, the missing items are worth INR 640, late delivery compensation is INR 49, the raita claim is held for review, and the partner-conduct claim receives INR 0. 

def calculate_refund(verdicts, evidence):
    amount = 0

    for verdict in verdicts:
        if verdict.status == "UPHELD":
            amount += pricing_table.amount_for(
                category=verdict.category,
                evidence=evidence
            )

    return amount

refund_amount = calculate_refund(verdicts, evidence)

if refund_amount > AUTO_APPROVE_CAP:
    return escalate_to_human(dispute_id)

The automatic refund is INR 640 plus INR 49, which equals INR 689. The LLM must not calculate, round, invent, or negotiate this number. Even a unanimous bench cannot override the automatic approval cap.

Stage 6: Write the customer response

Once the financial decision is complete, a low-temperature model can write the customer-facing message. It receives the final verdicts and the already calculated amount.

Operational considerations

The decision workflow explains how a refund is adjudicated. These sections explain how the system runs reliably in production.

Call budget and latency

The call pattern is: 

calls = 1 + (N x K) + 1

For four grievances and three judges:
1 + (4 x 3) + 1 = 14 LLM calls

Extraction and settlement each require one call. Judging requires twelve, so it dominates cost and latency. If those calls ran sequentially at roughly 1.5 seconds each, judging would take about 18 seconds.

With four concurrent workers, the twelve calls complete in three waves. At around 1-2 seconds per call, judging takes approximately 3-6 seconds. The concurrency must still be bounded: making one dispute faster is not useful if the overall system exceeds the provider rate limit.

Asynchronous processing and rate limits

The API should not keep a client connection open while fourteen model calls execute. It should create the dispute, return a dispute ID, and let workers perform the adjudication in the background.

  1. The client submits the complaint.
  2. The API creates the dispute record.
  3. The API writes an outbox event in the same transaction.
  4. An outbox publisher sends the event to Kafka or SQS.
  5. A worker consumes the dispute ID and checkpoints each stage.
  6. The client polls for status or receives a callback.

Why use a transactional outbox?

Without an outbox, the database write could succeed while queue publishing fails. The dispute would exist in the database but no worker would ever process it. The outbox stores the dispute and its pending queue event in the same database transaction, preventing that lost-request failure mode.

Handling HTTP 429 responses

At peak load, 200 disputes per minute multiplied by 14 calls produces approximately 2,800 LLM calls per minute. Rate-limit responses are therefore expected operating conditions. 

Attempt 1: wait 1 second + random jitter
Attempt 2: wait 2 seconds + random jitter
Attempt 3: wait 4 seconds + random jitter
Attempt 4: wait 8 seconds + random jitter

Exponential backoff reduces pressure over time. Jitter prevents many workers that failed together from retrying at exactly the same moment and causing another synchronized burst.

Storage and retention

A refund decision should preserve enough information to answer one question: why did this refund happen?

DataRowsApproximate size
disputes11 KB
grievances46 KB
evidence_snapshots13 KB

Total18Approximately 35 KB

The raw judge rulings are the largest part of the record. Keeping all twelve rulings supports customer appeals, internal investigations, model evaluation, debugging, and compliance audits.

At 30,000 disputes per day, 35 KB per dispute is approximately 1 GB per day, or about 380 GB per year. Raw judge rulings can remain in hot storage for 90 days and then move to cold storage, while financial records and evidence snapshots may require longer retention.

Complete workflow pseudocode

function process_dispute(complaint_text, order_id):

    dispute_id = hash(complaint_text + order_id)

    existing = ledger.get(dispute_id)

    if existing.status == SETTLED:
        return existing.settlement

    if existing.status == PROCESSING:
        return existing.status

    ledger.create_if_missing(
        dispute_id=dispute_id,
        complaint=complaint_text,
        order_id=order_id,
        status=RECEIVED
    )

    evidence = evidence_service.snapshot(order_id)
    ledger.save_evidence(dispute_id, evidence, status=INTAKE)

    grievances = extraction_model.run(
        complaint=complaint_text,
        line_items=evidence.line_items
    )
    validate_grievances(grievances)
    ledger.save_grievances(dispute_id, grievances, status=JUDGING)

    judging_tasks = []
    for grievance in grievances:
        for judge_number in range(3):
            judging_tasks.append({
                "dispute_id": dispute_id,
                "grievance": grievance,
                "evidence": evidence,
                "judge_number": judge_number
            })

    rulings = parallel_execute(
        function=judge_grievance,
        tasks=judging_tasks,
        batch_size=4,
        retry_policy=exponential_backoff_with_jitter
    )

    ledger.save_raw_rulings(dispute_id, rulings)
    verdicts = count_votes_by_grievance(rulings)
    refund_amount = pricing.compute(verdicts, evidence)

    if refund_amount > AUTO_APPROVE_CAP:
        ledger.mark_escalated(dispute_id)
        return human_review(dispute_id)

    ledger.save_verdicts(dispute_id, verdicts, refund_amount, status=TALLIED)

    message = settlement_writer.run(
        complaint=complaint_text,
        verdicts=verdicts,
        amount=refund_amount
    )

    payment = payments.refund(
        idempotency_key=dispute_id,
        amount=refund_amount
    )

    ledger.save_settlement(
        dispute_id=dispute_id,
        message=message,
        payment=payment,
        status=SETTLED
    )

    return {
        "dispute_id": dispute_id,
        "refund_amount": refund_amount,
        "message": message,
        "verdicts": verdicts
    }

Challenges and troubleshooting

All judges return the same answer

Check the temperature and request construction. At temperature zero, repeated calls may be effectively deterministic. Use a non-zero temperature for judgement calls, while keeping settlement generation at a low temperature.

The extractor drops unsupported claims

If the extractor removes “the delivery partner was rude” because there is no direct evidence, extraction and judgement have been mixed together. Add an explicit instruction: “Do not judge whether the grievance is true. Only extract it.”

Missing evidence becomes rejection

If the system has no packaging record, it cannot conclude that the raita did not leak. The correct result is escalation, not rejection. 

Evidence supports claim      -> UPHELD
Evidence contradicts claim   -> REJECTED
Evidence is silent/ambiguous -> ESCALATE

Duplicate refunds

Workers can retry after timeouts. Use the same idempotency key for every payment retry: idempotency_key = dispute_id. The ledger should also prevent a settled dispute from being processed again.

Queue messages are processed twice

SQS and similar queues provide at-least-once delivery. Use a visibility timeout longer than the expected job duration, heartbeats for long-running jobs, stage checkpoints, idempotent processing, and payment idempotency keys.

The refund exceeds the cap

Enforce the cap in application code before calling the payment provider. Do not branch a payout on the model's confidence value. Confidence is model-generated; the cap is a deterministic safety boundary.

Conclusion: What makes the bench reliable?

The Refund Bench turns one emotional paragraph into four explicit, testable grievances: late delivery, missing items, leaked packaging, and partner conduct. Each grievance is evaluated independently against the same frozen evidence.

  • Extract grievances before judging them.
  • Resolve vague references into self-contained claims.
  • Freeze evidence before model evaluation.
  • Run independent judges without shared history.
  • Count votes in application code.
  • Treat missing evidence as escalation, not rejection.
  • Calculate refund amounts deterministically.
  • Enforce a hard automatic approval cap.
  • Use idempotency keys to prevent duplicate payments.
  • Use queues and workers for asynchronous processing.
  • Retry rate-limit failures with exponential backoff and jitter.
  • Retain raw rulings for auditability and debugging.

The key boundary is simple: the model can interpret the complaint and write the explanation, but the application decides whether money moves and how much. That separation turns an impressive prototype into a system that can be operated responsibly.
